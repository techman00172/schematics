# FURS — How to Write Readable Forth Without Blowing Up Your Flash

Podcast document for NotebookLM Audio Overview.
Target: male/female co-host, natural conversational style.

---

Picture this: you are an embedded systems developer, and you have just started a new project on an STM32F051 microcontroller. It has sixty-four kilobytes of flash memory, which sounds like a lot when you are writing assembly. But you are not writing assembly. You are writing Mecrisp-Stellaris Forth, and you want your code to be readable. You want to write register names like GPIOC_BSRR_BS9 instead of the raw hexadecimal address four-eight-zero-zero-zero-eight-one-eight. You want the CMSIS standard names that ARM and STMicroelectronics defined, the ones that every C programmer on this chip takes for granted.

Here is the problem: Mecrisp-Stellaris Forth stores every word you define in a dictionary. That dictionary lives in flash. And if you were to compile all thirty-seven hundred CMSIS register and bitfield names as dictionary entries, they would consume roughly twenty-nine kilobytes of your sixty-four. That is almost half your flash, gone, before you have written a single line of application logic. You would be paying a forty-five percent memory tax just to have nice names.

That is where FURS comes in. FURS stands for Forth Upload Replacement System. It is a build pipeline that lets you write Forth source code using beautiful human-readable CMSIS names, while the actual code that lands on the chip contains nothing but raw absolute addresses and bit offsets. The names themselves never touch the microcontroller. They are resolved at build time, on your development machine, using a set of Unix command-line tools you already have: a text processor called gema, the XML toolkit xsltproc and xmllint, and SQLite.

The philosophy is dead simple: keep the CMSIS dictionary on the host, not on the target. The same way a C compiler resolves symbolic register names into absolute memory addresses at compile time, FURS resolves CMSIS Forth words into absolute addresses and bit manipulation instructions at upload time. And it saves you twenty-nine kilobytes of flash in the process.

Now let us walk through what that actually looks like in practice.

You open your editor and you write a line of Forth that says:

GPIOC_BSRR_BS9 1 bfs!

To a Mecrisp-Stellaris Forth interpreter, that line is nonsense. There is no word called GPIOC_BSRR_BS9 defined anywhere in the dictionary. If you tried to type that into the REPL, the interpreter would throw an error. But you are not typing it into the REPL. You are writing it into a source file that will go through a four-stage transformation pipeline before it ever reaches the chip.

The first stage of the pipeline takes your source file and runs it through gema with a pattern file called bitfields.pat. This pattern file was auto-generated from the official ARM CMSIS-SVD XML file for the STM32F051. It contains over seven thousand substitution rules, one for every bitfield on every register on every peripheral in the chip. The rule for GPIOC_BSRR_BS9 looks like this: whenever gema sees that text, it replaces it with a dollar sign, the absolute address four-eight-zero-zero-zero-eight-one-eight, then in parentheses the bit width which is one, then another parenthesis with the bit offset which is nine, followed by an exclamation mark. So your readable line becomes:

four-eight-zero-zero-zero-eight-one-eight ( 1 ) 9 1 bfs!

Now bfs! is a real Forth word, defined in the FURS utility library. It takes a value, a bit offset, a bit width, and an address, and it writes only those bits to that register. It is an atomic bit-field set operation. The chip knows exactly what to do, because every number is now a raw hardware address or a bit position.

But wait. Your source file might also contain register-level references without bitfield granularity. A line like:

TIM2_CNT @

The second stage of the pipeline catches these. A second pattern file, registers.pat, generated from the same SVD, substitutes TIM2_CNT with four-zero-zero-zero-zero-zero-two-four, the absolute address of the timer two counter register. So the chip sees:

four-zero-zero-zero-zero-zero-two-four @

The third stage handles symbolic constants. Instead of writing GPIO pin mode configuration as magic numbers, you write ANALOG, AF, OUTPUT, PUSH-PULL, OPEN-DRAIN. The constants.pat file swaps these for their actual binary values: %11, %10, %01, and so on.

The fourth and final stage runs strip.pat, which removes all whitespace, all comments, and all stack effect notations. What is left is a minimal, dense Forth binary that Mecrisp-Stellaris can compile directly. This stripped file is called upload.fs, and it is the artifact that gets flashed to the chip.

So where did all these pattern files come from? This is where the rest of the pipeline earns its keep.

Everything starts with the official CMSIS-SVD file for your microcontroller. STMicroelectronics publishes this for every STM32 family. It is an XML file that describes every peripheral, every register, and every bitfield in the chip, including their base addresses, offsets, access modes, reset values, and descriptions. FURS takes this file and runs it through a series of XSLT transforms.

First, the SVD is cleaned. A simple gema pattern strips extraneous whitespace and replaces the C-style zero-x hex notation with the Forth-style dollar sign notation. Then an XSLT stylesheet called unfolded.xsl resolves all the derivedFrom attributes — SVD files use these to share register definitions between similar peripherals, and unfolding them makes every peripheral self-contained.

Next comes the critical step: absolute address resolution. The raw SVD stores register addresses as a base address plus an offset. The process-hex2num XSLT transform, using a custom hex-to-decimal recursive template, adds these together and writes the absolute address for every register in the cleaned XML. At this point, you have an SVD file where every register has a concrete, usable hardware address.

From this resolved SVD, two things are produced in parallel. One workstream generates the gema pattern files we just described — bitfields.pat and registers.pat — by running XSLT stylesheets that iterate over every register and field and write gema substitution rules. The other workstream generates SQLite databases.

Two databases are built: a relational database and a flat database. The relational database has three tables — peripheral, register, and field — linked by foreign keys. The flat database creates one table per peripheral. These databases let you query the chip's memory map interactively. You can search for every register containing the letters C N T, or dump all fields of the RTC peripheral, or find every bitfield that mentions reset in its description. A command-line shell script called furs-cli-relational wraps this up with a simple search interface.

This whole pipeline, from SVD to uploadable binary, is driven by a Makefile. The Makefile coordinates three parallel workstreams: the Forth source transformation, the relational database build, and the flat database build. Running make all regenerates everything. Running make upload sends a signal to the SWD debug daemon, which reloads the newly built upload.fs and flashes it to the chip.

Speaking of the debug daemon: FURS uses a tool called swd2, which is a FreeBSD binary that acts as an SWD upload daemon. It connects to the STM32F051 through a debug probe, listens for a SIGQUIT signal, and on receiving it, reads upload.fs from disk and programs the chip's flash. A Python readline wrapper called swd2rl.py provides a comfortable interactive Forth REPL with tab completion for dictionary words and a persistent command history. This means your development cycle is: edit source, run make all, run make upload, and test your code in the REPL, all from the terminal.

To make all of this concrete, let us look at the demo application that ships with FURS. It reads temperature from an LMT-01 sensor, which is a two-pin digital temperature sensor that outputs a pulse train whose count is proportional to temperature. The demo is about two hundred lines of Forth, spread across six source files, and every single register access uses CMSIS names.

The system boot file sets up the Cortex-M0 to run at forty-eight megahertz using the internal HSI oscillator with PLL. It configures the SysTick timer at one-millisecond intervals and installs a calltrace handler that will dump the return stack if an unhandled interrupt fires — a debugging lifesaver on a chip with no JTAG.

The GPIO configuration file sets up eight pins across three ports. Pin PA1 is set to analog mode for the comparator input. Pin PA5 is configured as an alternate function for the TIM2 external clock input. Pins PA6 and PA12 are set as comparator outputs. Pin PC1 powers the LMT-01 sensor. And PC8 and PC9 drive the blue and green user LEDs on the Discovery board. Every single pin mux configuration uses CMSIS bitfield names like GPIOA_MODER_MODER1 or GPIOC_OSPEEDR_OSPEEDR1.

The comparator configuration file sets up COMP1 and COMP2 for LMT-01 pulse detection. It configures the comparators to use half of the internal voltage reference as their threshold, selects appropriate speeds and hysteresis levels, and enables window mode where COMP2 tracks COMP1. These are all written as straightforward register writes using CMSIS names.

The pulse file configures TIM2 in external clock mode, where it counts pulses from the comparator output. The timer's slave mode control register is set to external clock mode one, and the trigger selection points to the external trigger input. A sampling filter is enabled to debounce the signal.

The main application ties it all together. The init word runs at boot and calls all the initialization words. There is a measurement word that powers on the LMT-01 for one hundred milliseconds, captures the TIM2 pulse count, and powers it off. A conversion word transforms the raw count into degrees Celsius using the LMT-01 formula: divide the count by 4096, multiply by 256, subtract 50. There is also a Fahrenheit conversion. The temperature question-mark word runs a full measurement cycle with error checking — it verifies the LMT-01 count falls within the valid range before attempting conversion.

The entire demo compiles to about six kilobytes of flash, including all the initialization, measurement, and conversion logic. The CMSIS name resolution added zero bytes to the chip, because it happened entirely on the host.

So here is why this matters for you, the Mecrisp-Stellaris Forth developer starting a new project on a new STM32 chip.

The FURS pipeline is completely chip-agnostic at the design level. You swap in your chip's SVD file, run the pipeline, and you get gema patterns for that specific MCU's register map. The Makefile targets do not change. The XSLT transforms do not change. The Forth utility words — bfs!, bfc!, enable!, disable! — do not change. The only thing that changes is the SVD file, and therefore the generated patterns that map CMSIS names to addresses.

The toolchain is deliberately simple. Gema is a single-file portable C program that builds with any C compiler. XSLT processing is done by xsltproc, which ships with every libxslt installation. The databases are plain SQLite3 files that require zero configuration. There is no Python virtual environment to manage, no Node modules to install, no Docker container to pull. If you have a Unix system and a C compiler, you can build and run the entire pipeline.

The interactive REPL, driven by swd2rl.py, gives you a comfortable development experience: tab completion for Forth words, command history that persists across sessions, and the ability to test hardware interactions live. You can type TIM2_CNT @ . and instantly see the current timer count, even though TIM2_CNT is not a word in the dictionary — because the CMSIS resolution already ran before the word was sent to the chip.

The library of reusable Forth words ships with additional goodies: a disassembler for Cortex-M0 that lets you inspect compiled code, memory usage statistics that read the chip's flash size register, and a calltrace handler that gives you a stack trace when things go wrong. These are not part of the core CMSIS pipeline, but they are the kind of tools every embedded Forth programmer eventually builds, and they are here waiting for you.

To get started, clone the repository, drop your STM32's SVD file into the project root, run make all, and connect your debug probe. Your source files will read like documentation and compile like assembly. That is the promise of FURS.

And if you are wondering about the name: FURS stands for Forth Upload Replacement System. But honestly, the name does not matter. What matters is that you can write GPIOC_BSRR_BS9 instead of a six-digit hex address, and your chip will never know the difference. That is the whole point.
